# PROMPT：新增 `/design` 讨论式方案 skill

## 背景

现有工作流（`/start` → `/finish`、`/quick`）都假设**需求已经明确**：人给出 prompt，Agent 计划、执行、总结。

但实际上常有另一类需求：不确定该怎么落地，甚至不确定需求本身是什么，需要和 Agent **在讨论中逐步收敛出一个框架级方案**。这类讨论的特点：

- 是多轮对话，逐步推进，最初的描述只是起点，没有特殊地位；
- 产出的方案可能非常宏大，未必落到可执行计划，之后可能分很多轮去做，也可能根本不做；
- **方案本身就是这一轮的最终产出**。

`/start` 不适合：它要求先有明确 PROMPT、再 PLAN、再执行、再 SUMMARY。直接用 CC 的 plan mode 也不适合：它的产物不进仓库、不记录讨论过程、退出即进入执行，长讨论中途还会被上下文压缩丢掉推理与决策。

## 需求

新增 `/design` skill，引导用户从一段背景描述出发，经多轮对话得到最终方案，并留下两份记录：

1. **讨论记录** —— 整理过程中用户给的背景和信息输入、Agent 的观点 / 分析 / 判断、用户据此做的关键决策；
2. **方案本身**。

## 已决（对话中与用户确认）

- **落点**：`docs/design/<中文主题>/`，目录名不编号。不放顶级 `design/`：`docs/design/` 正是理想结构（`docs/design/` + `docs/develop/`）的一半，将来若迁移轮次目录无需再搬；且顶级 `design/` 在前端项目里容易与设计稿目录撞名。把现有 `docs/<N>-*` 迁到 `docs/develop/` 本轮不做。
- **产物只有两份**：
  - `DISCUSSION.md`：不单设 PROMPT，最初的背景描述就是阶段 0；之后每个阶段记「用户信息输入 / Agent 分析判断 / 用户决策 / 被否选项及理由」，决策即时追加，不等收尾再整理；
  - `DESIGN.md`：方案本身，顶部写状态（`讨论中` / `已定稿` / `已搁置`）与日期，不要求落到可执行粒度。
- **不开 worktree**，讨论期间不改代码，支持 `--resume <主题>` 跨会话续聊。
- **收尾**：只定稿 `DESIGN.md` 并 `/commit`；**不拆 issue、不碰 DEVTREE、不写 SUMMARY**。
- **与开发轮次单向引用**：round 的 `PLAN.md` 可引用某份 design，design 不反向维护。
- **仅支持仓库内**，不设仓库外落点。
- **同步宪法**：在 `GLOBAL_AGENTS.md`「核心开发模式」补一段说明这种形态及其对 `SUMMARY.md` 的豁免。
