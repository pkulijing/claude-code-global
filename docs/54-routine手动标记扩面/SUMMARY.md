# 开发总结：`/routine-docs` → `/routine-dev`，加 owner 标记通道并放开落点

## 开发项背景

`/routine-docs` 上线后运行正常，但**对「要不要把一条 issue 纳入开发」过于保守**，导致一批本来完全够格自动做掉的 issue 长期躺在 backlog 里 —— 简单的 skill 修改与新建、明确的 template 增补、边界清晰的 bug 修复。

保守的源头不是判断力不足，而是两条硬边界：

1. **落点白名单只有文档**（`playbooks/*.md`、`GLOBAL_AGENTS.md`、`README.md`、`docs/`），明令禁止 `skills/*.md` 与一切可执行面；
2. **模型分诊的四类排除只能保守判** —— 判错的代价不对称（做错一条自动 PR 比漏收一条贵得多），于是宁可漏收。

**关键认识：「落点只限文档」不只是范围设定，它同时是一道安全机制。** issue 正文来自公开仓、任何人都能写，是 prompt-injection 面；正是「改动只落文档」在替「输入不可信」兜底 —— 文档写错了人下次读到就发现，脚本写错了每次工具调用都在执行它。

所以放开落点不能只是「把白名单加长」，必须**先给那道被撤掉的防线找一个等价替代**。

## 实现方案

### 核心设计：两条通道，授权强度不同

| 通道 | 谁决定纳入 | 能改什么 |
| --- | --- | --- |
| **自动通道** | 模型分诊（保守判） | 只有文档落点 |
| **标记通道** | **owner 打 `auto:take` label** | 放开到 `skills/`（除自己）/ `templates/` / `scripts/` / `hooks/` |

`auto:take` 的语义定死为一句话：**「owner 已过目此条，背书其正文可被无人值守执行」**。它把被撤掉的机制性防线换成**人工背书** —— 是**授权**的转移，不是**风险**的消失。

**未标记 issue 的分诊行为完全没变**：本轮只增加一条人工通道，不放松任何自动判定的保守度。

### 为什么选 label 而非评论做闸（人类拍板，实证支撑）

需求最初的提法是「手动加评论」。实测后改为 label 做闸、评论降级为可选补充：

- **公开仓任何人都能评论**（`authorAssociation` 会是 `NONE`），纯评论方案必须自己校验作者身份；而 **label 只有有写权限的人打得上**，授权强度由 GitHub 权限模型保证，不靠我们校验。
- 云端读 label 的路径在现有流程里已实测跑通；**读评论的 MCP 工具能力未经实测**，押在它上面会让整个机制在云端静默失效。

评论仍然有用，但只作**实现提示**：`issue-view --with-comments` 输出 `ownerHint`（最新一条 OWNER 评论），**读不到不阻断**。

### 划分判据：标记覆盖「保守性」排除，覆盖不了「事实性」排除

这条划分是本轮最有价值的产物，它让「标记之后还要不要判断」有了可操作的答案：

| 类别 | 例子 | 标记通道 |
| --- | --- | --- |
| **保守性**（怕自动做砸） | P0、需讨论选型、需落 PLAN 长期追踪、落点非文档 | **覆盖** —— 标记本身就是拍板 |
| **事实性**（做不出来 / 不该做） | 正文没说清、现状已满足、`wontfix` 矛盾、撞红线 | **不覆盖** —— 跳过并在 PR 里点名 |

**「我授权你做」不等于「你必须做出来」。**

### 四条红线（计划三条，实施中增为四条）

`skills/routine-dev/**`（自己）、**`agents/**`（自己的检查员）**、`install.sh`、`.github/**` —— 打了 `auto:take` 也解不开。

`agents/**` 是 **PLAN 里没有、实施中新增的**：本轮 rebase 到 master 时并入了 round 53「review 成本与思考深度调优」，它引入 `agents/` 目录来钉死 review 编队的 `model` / `effort`。那正是**本 routine 自己每个 commit 都要过的那道门禁的强度** —— 能改自己的检查员，与能自改 SKILL 是同一条权限提升链，只是隔了一层。

`references/security-boundary.md` §7 把前两条归并成一句通则，供以后照此判断：

> **routine 不得修改任何决定「它自己被允许做什么」或「它自己被怎样检查」的东西。** 以后再往仓库里加这类元层面配置，默认按红线处理。

§7 还**明写了这条论证的已知弱点，不粉饰**：owner 打 label 时未必逐字读过长正文里埋的一段 —— 攻击链没有失效，只是把要骗过的对象从「分诊模型」换成了「打 label 的人」。补偿因此是纵深的：PR 仍是最终闸口 + 触及可执行面强制显著标注 + 外部文本一律当数据。

### 顺带补上的一个洞：撞车防线从单向改为双向

`/routine-slim` 早就会排除「在途 PR 碰过的文件」，但 `/routine-dev` 的幂等**只按 `Closes #N` 排除 issue、不看文件** —— slim 周日出的 PR 会被周一的 dev 从背后撞上。放开 `skills/**` 后两者主业重叠，这个洞会更常触发。

**改法只有一处**：Step 3 落点复核的并集**初始值从空集改为「所有 open PR 碰过的文件」**。一处初始化改动，防线补成双向，且顺带覆盖了人手开的 PR。

### 额外产物

- **`platform_issue.py` 新增 `issue-view --with-comments`**：输出 `comments` 与 `ownerHint`。**默认 schema 零变化**（实测新旧版本对同一 issue 的输出字节级相同），`/start` 等既有消费方不受影响。
  **owner 身份判据（只认 `OWNER`、取最新一条）刻意下沉进代码并挂单测**，而不是留给模型每次运行自觉过滤 —— 这是授权判据，不该依赖模型自律。
- **`unlink_legacy_dir` 泛化**：原先写死只认 `/*/rules`，改名清理复用不了。参数化目标路径而非复制一份 —— 目录改名这件事以后还会发生。沙盘测试 9 → 12 条。
- **`.github/labels.yml` 新增 `auto:take`**。
- **分支前缀 `auto/docs-*` → `auto/dev-*`**，但 Step 0.5 的认领判据**同时认历史前缀**，防止老 PR 失联（改动时零在途 PR，迁移窗口本就干净）。

### TDD 执行情况

两处代码改动都走了「先红后绿」：`platform_issue.py` 先写断言拿到 `NameError`，`unlink_legacy_dir` 先加用例 9 看它 FAIL。**且用探针验证了测试不是假绿** —— 把 `case` 判据改成恒真，用例 10 确实变红。

## 局限性

1. **`auto:take` 的授权强度取决于 owner 打 label 时是否真读了正文。** 长 issue 里埋一段面向 agent 的指令仍可能被放行。这是设计上接受的残余风险，已在 reference §7 明写，不是疏漏。
2. **云端读评论未经实测。** `ownerHint` 在云端大概率取不到（GitHub MCP 是否有读评论工具未知）。设计上不阻断，但意味着**标记通道在云端实际只有 label 一条信息**，issue 正文必须自己写清楚。
3. **GitLab 端 `--with-comments` 不可用**：`glab` 本机未安装、其 notes 能力无法实测，故返回空数组 + stderr 明确说明，**不猜一个「看着对」的命令**。本仓是 GitHub，不受影响。
4. **同模型自审的盲区，后果比以前重了。** `/review-loop` 与写 diff 的同为 Claude 家族，而本轮把它的把关对象从文档扩到了可执行代码。跑单测是对冲手段，但只覆盖有单测的文件。
5. **放开后的真实产出质量完全没有实证。** 本轮所有验证都是机械的（单测 / check-refs / 引用一致性），**没有跑过一次带 `auto:take` 的真实 dry-run** —— 分诊规则贴不贴合真实数据的分布，只能实测。这正是 `playbooks/cloud-routine.md` §5 立规矩的场景。

## 可沉淀项

1. **「不得修改决定自己权限或自己如何被检查的东西」是一条通用的 agent 安全判据**，不止适用于本仓的两条 routine。任何有自动写权限的 agent 都该有这条。**去向**：本仓 `GLOBAL_AGENTS.md` 候选，但边界与措辞要想清楚（判据见下方 Step 3 反思）。
2. **「授权转移 ≠ 风险消失」的划分方法**（保守性排除 vs 事实性排除）：凡是「加一个人工开关来放宽自动化边界」的设计都适用 —— 开关能免掉的是「怕做错」，免不掉「做不到」。
3. **写测试时要用探针验证它不是假绿**：本轮用例 10 初版就是假绿（沙盘造得不对，第二道防线替被测判据兜了底），是 reviewer 主动去改坏实现才发现的。**TDD 的「先红」只证明测试当时会红，不证明它红在你以为的那个判据上。**
