## 二、#114 的需求：`/start` 开轮前的远端对齐

### 2.1 根因

`/start` 目前**完全不碰远端**：

- issue 详情走 `platform_issue.py issue-view <N>`，拿的是 issue 正文，**但不检查它是否已被关闭**；
- 轮次编号的三源并集（本树 `docs/` / 在途分支 / 其它 worktree 的 `docs/`）**全是本地信号**，远端已有的 `docs/<N>-*` 一概看不见 —— round 55 因此把编号算成 53，而远端 53、54 都已占用。

多设备并行开发（本仓正是这个场景：多台机器 + 云端 routine 都在写）下，这两个盲区必然撞车。

### 2.2 issue 原文给出的建议修法

在 `/start` 的**通用流程第 1 步之前**加一步「远端对齐」：

1. `git fetch origin`（只更新 remote-tracking，不改工作区，安全）；
2. **issue 驱动分支**：检查目标 issue 是否已被远端关闭 —— `git log origin/<主分支> --grep "Closes #<N>" --oneline`，命中则**停下报告**（附那个 commit 的 hash / 标题 / 日期），让人类决定是「不做了」「只补增量」还是「远端修得不对，重做」；
3. **轮次编号的三源并集加第四源**：远端 `git ls-tree --name-only origin/<主分支> docs/` 解析出的编号，避免与远端已合入的轮次撞号。

### 2.3 约束

- fetch 失败（离线）**不应阻断开轮**，降级为「跳过远端检查并明确提示」。
- 本条只改 `/start`，**不动 `/finish` 的收尾逻辑**。

## 三、#116 的需求：宪法补撞车决策路径

### 3.1 为什么值得固化

这不是「计划的技术假设被证伪」（宪法已有「停机义务」覆盖那种情形），而是**交付物本身被别人先做了**，且两边各有对方没有的内容。选哪条路代价差异很大：

- **弃己方、只补增量** —— diff 小、无双写漂移；代价是丢掉己方独有的表达形式与部分内容；
- **硬 rebase 合并两版** —— 保留全部；代价是同段落双方都重写过，冲突极难解，解完还要手工去重、改轮次编号、重做 DEVTREE、改写 SUMMARY；
- **保留己方覆盖远端** —— 会丢掉远端独有的设计（round 55 若这么做，会丢掉「无人值守例外」这条关键设计）。

round 55 靠人类当场拍板。但这类撞车在多设备 + 云端 routine 并行的仓库里**会反复出现**，值得给出稳定判据。

### 3.2 issue 原文给出的建议判据（初稿）

作为宪法「计划假设被证伪时的停机义务」的一个**具体子类**补充：

发现远端已实现同一需求时 → **停机**，先做差异盘点（逐条列「远端有 / 己方有 / 双方都有」），再按下述取舍并请人类确认：

| 情形 | 处理 |
| --- | --- |
| 远端已覆盖且更全面 | **弃己方**，只在远端基础上补真增量；己方版本打备份 tag 留档 |
| 各有独有价值 | 取增量合并到远端版本之上，**不硬 rebase**（同段落双改的冲突成本高于重写） |
| 己方更全面 | 保留己方，但必须逐条说明远端版本的哪些点已被吸收 |

配套硬要求：**弃掉的工作必须打备份 tag 并在 SUMMARY 里写明弃因**，避免后来者（或未来的自己）翻到那段历史时误以为是被否决的设计 —— round 55 的 reviewer 就真的翻到了弃用分支并花了力气评估它是否「重蹈已放弃的设计」。
